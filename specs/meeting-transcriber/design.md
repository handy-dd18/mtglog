# 設計: 会議音声のローカル文字起こし

## 1. 全体構成

```
Windows                                   WSL2（または Docker）
┌──────────────────────────┐             ┌────────────────────────────────────────┐
│ Teams / Zoom アプリ        │             │ 文字起こしサーバー（Python, FastAPI）       │
│   └─ 音声出力 → ヘッドセット │             │                                        │
│                          │             │  GET /          取得ページの配信          │
│ Edge: http://localhost:8765 │  WebSocket  │  WS  /ws        音声受信・結果送信        │
│  取得ページ                 │ ──────────▶ │   ├─ チャンネル別の発話区間検出（VAD）     │
│   ├─ getUserMedia → 自分    │ ◀────────── │   ├─ 文字起こしワーカー（faster-whisper）  │
│   └─ getDisplayMedia → 相手 │   結果       │   └─ 結果の書き出し（output/）            │
└──────────────────────────┘             └────────────────────────────────────────┘
```

Windows 側で動くのは Edge で開く取得ページだけである（C-1）。ページはサーバーが配信する静的ファイルで、外部の資源を読み込まない（REQ-6.3）。

## 2. 取得ページ（web/）

### 2.1 画面

1 枚のページに、次の 4 つを上から並べる。無音の警告（2.6）は、状態表示の下の通知欄に出す。

1. 状態表示。「記録中」「停止中」「再接続中」を色つきで常に表示する（REQ-6.4）。
2. デバイス。マイクの選択欄と、その下に並べた「スピーカー（相手の声の取得元）」の表示、案内、警告欄（REQ-1.1〜1.3, 1.6）。
3. 操作。「開始」「停止」ボタンと設定（言語、マイクの音声処理、録音保存）。
4. 文字起こし結果。確定した発話を時刻・話者つきで追記表示する（REQ-4.3）。

### 2.2 デバイスの列挙と初期選択

ブラウザーはマイクの利用を許可されるまでデバイス名を返さない。そこでページを開いた直後に既定のマイクで `getUserMedia` を 1 回呼んで許可を得てから、すぐにそのトラックを止め、`enumerateDevices` で一覧を取る。

- 入力デバイスの初期選択は次の順に決める（REQ-1.2, 1.4）。
  1. 前回選んだデバイス（`localStorage` に保存した `deviceId`）が一覧にあればそれ。
  2. 名前がヘッドセットを示す語のいずれかを含むデバイスのうち、一覧で最初のもの。語の一覧はサーバーの設定から受け取る。
  3. `deviceId` が `default` のデバイス。
- 既定の再生デバイスは、`kind` が `audiooutput` で `deviceId` が `default` の項目から名前を取る。Chromium はこの項目の名前を「既定 - 〈実デバイス名〉」の形で返す。実デバイス名がヘッドセットを示す語を含まないとき、警告欄に「既定の再生デバイスがヘッドセットではない可能性があります。相手の声が取れないことがあります」と表示する（REQ-1.3）。
- スピーカーの欄（REQ-1.3, 1.6、2026-10-22 改訂）。マイクの選択欄と同じ形の行に、「スピーカー（相手の声の取得元）」として上の実デバイス名を表示する。選択欄にはせず、名前だけを表示する。ブラウザーは、システム音声を取る再生デバイスを選べないためである。行の下に次の案内を常に表示する。
  - 「スピーカーはこのページでは変えられません。Windows の［設定］→［システム］→［サウンド］→［出力］で変えてください。」
  - 「Teams / Zoom のスピーカーも同じデバイスにしてください。違うデバイスに出た音は記録されません。」
  - 案内の横に、Windows のサウンド設定を開くリンク（`ms-settings:sound`）を置く。Edge は開く前に確認を求める。開けない環境でも、上の案内の文で手順が分かるようにする。
- `devicechange` イベントで一覧を更新する。記録中に選択中のマイクのトラックが `ended` になったら、記録は続けたまま警告を出し、選び直したマイクで「自分」チャンネルの取得を再開する（REQ-1.5）。「相手」チャンネルは止めない。
- 記録中に `devicechange` を受けたら、サーバーに `device_changed` を送る（4.2）。サーバーはこれを REQ-2.7 の計測の起点にする（3.6）。

### 2.3 音声の取得

「開始」を押すと、次の順に処理する。

1. 選択中のマイクを `getUserMedia({audio: {deviceId: {exact: id}, echoCancellation, noiseSuppression, autoGainControl}})` で開く。3 つの音声処理の値は設定に従う（REQ-2.6）。
2. `getDisplayMedia({video: true, audio: {systemAudio: "include", windowAudio: …}, systemAudio: "include", monitorTypeSurfaces: "include"})` を呼ぶ。利用者は画面共有の選択画面で「画面全体」を選び、「システム音声も共有する」を有効にする。`windowAudio` は V3 の結果で決める（REQ-2.3）。
3. 返ったストリームに音声トラックがなければ、ストリームを止め、「音声を共有する」を有効にして選び直すよう案内して終了する（REQ-2.4）。
4. 映像トラックは使わないが、止めると音声も止まる可能性があるため（V7）、`applyConstraints({frameRate: 1, width: 320})` で負荷を下げて保持する。

### 2.4 音声の変換と時刻の付け方

`new AudioContext({sampleRate: 16000})` を 1 つだけ作り、2 本のストリームをそれぞれ `MediaStreamAudioSourceNode` → `AudioWorkletNode` につなぐ。標本化周波数の変換はブラウザーに任せる。

両チャンネルを同じ AudioContext で処理するので、AudioWorklet 内の `currentFrame`（その AudioContext の開始からの標本数）を共通の時刻基準として使える（REQ-2.5）。ワークレットは 32 ビット浮動小数点の標本を 16 ビット整数に変換し、1,600 標本（100 ミリ秒）ごとに、先頭標本の `currentFrame` を添えてメインスレッドへ渡す。記録開始時の `currentFrame` を記録の原点とし、サーバーへはそこからの差を送る。

送信はワークレットからのメッセージを受けたときに行い、`setTimeout` などのタイマーには頼らない。背景タブではタイマーが間引かれるが、AudioWorklet は音声スレッドで動くので間引かれない（REQ-5.4、V5 で確認）。

### 2.5 再接続と送信待ちバッファ

ページはチャンネルごとに、送信済みだがサーバーからの受領確認がない音声フレームを最大 60 秒分保持する（REQ-5.3）。60 秒を超えた分は古い順に捨て、捨てた区間を画面に表示する。接続が切れたら 1 秒、2 秒、4 秒（以後 4 秒間隔）で再接続を試み、つながったら `resume` メッセージで続きから送る（4 章）。

### 2.6 無音の警告の表示（REQ-2.7, 2.8、2026-10-22 追加）

判定はサーバーが行い（3.6）、ページは `silence` メッセージ（4.2）を受けて通知欄に警告を出す・消す。

| `kind` | 表示する文 |
|---|---|
| `remote` | 「相手の音声が {n} 分間届いていません。Teams / Zoom のスピーカーと Windows の既定の再生デバイスが同じか、画面共有で『システム オーディオも共有する』をオンにしたかを確かめてください。」 |
| `both` | 「自分と相手のどちらの音声も {n} 分間届いていません。マイクが音を拾っているか、スピーカーの設定が合っているかを確かめてください。会議が終わっていれば、記録を停止してください。」 |

- 警告には閉じるボタンを付ける。閉じても記録は続く。閉じた警告は、同じ `kind` の `active: false` を受けるまで再表示しない。
- `active: false` を受けたら警告を消す。

## 3. 文字起こしサーバー（server/）

### 3.1 モジュール

| モジュール | 役割 | 主な要件 |
|---|---|---|
| `app` | FastAPI のアプリ。静的ファイルの配信と WebSocket の受け口 | REQ-5.1, 6.2 |
| `session` | 記録 1 回分の状態（記録 ID、チャンネルごとの受信位置、出力先） | REQ-4.1, 5.3 |
| `segmenter` | チャンネルごとに発話区間を切り出す | REQ-3.2 |
| `transcriber` | 文字起こしワーカー。モデルを 1 つだけ読み込み、発話区間を順に処理する | REQ-3.1, 3.3, 3.5 |
| `writer` | 結果を JSON Lines と Markdown に追記し、必要なら WAV を書く | REQ-4.1, 4.2, 4.4 |
| `config` | 設定ファイルとコマンドライン引数の読み込み | REQ-1.2, 3.1 |
| `silence` | チャンネルごとの発話の有無から、無音の警告を判定する（3.6） | REQ-2.7, 2.8 |

### 3.2 発話区間の切り出し

チャンネルごとに Silero VAD を 512 標本（32 ミリ秒）単位で流し、次の規則で発話区間を確定する。

- 発話確率が 0.5 以上になった時点を発話の開始とし、その 200 ミリ秒前から区間に含める（語頭の欠け防止）。
- 発話確率 0.35 未満が 600 ミリ秒続いたら発話の終了とする。
- 区間が 20 秒を超えたら、直近で発話確率が最も低い位置で強制的に区切る。発話の切れ目を待つと遅延が REQ-3.3 を超えるためである。
- 250 ミリ秒未満の区間は捨てる（咳や物音）。

確定した区間は、記録の原点からの開始・終了の標本位置とチャンネル名を付けて、文字起こしワーカーのキューに入れる。

### 3.3 文字起こしワーカー

起動時に faster-whisper のモデルを 1 つ読み込み、別スレッドで 1 つのキューを先着順に処理する。2 チャンネルで 1 つのモデルを共有するのは、6 GB の VRAM に `large-v3-turbo` を 2 つ載せる余裕がないためである。

- 呼び出し: `model.transcribe(audio, language=設定値, vad_filter=False, beam_size=1, condition_on_previous_text=False)`。区間の切り出しは 3.2 で済ませているので VAD は無効にする。前の文脈を引き継がないのは、片方のチャンネルの文脈がもう片方に混ざるのを避けるためである。
- モデルは 5.3 で準備した手元のディレクトリから読み込む。インターネットからは取得しない（2026-10-22 改訂）。
- 起動時に CUDA で読み込めなければ、`small` / `int8` / CPU で読み込み直し、警告をログに出す（REQ-3.5）。
- キューの待ち時間と処理時間を発話ごとにログへ出し、REQ-3.3 の遅延を計測できるようにする。

### 3.4 出力

記録を開始するたびに `output/<YYYYMMDD-HHMMSS>/` を作る（REQ-4.1）。

| ファイル | 内容 | 書き方 |
|---|---|---|
| `transcript.jsonl` | 1 発話 1 行の JSON | 確定のたびに追記して `flush` する（REQ-4.2） |
| `transcript.md` | 人が読む形式 | 確定のたびに追記する。停止時に開始時刻順に並べ直して書き直す |
| `me.wav`, `remote.wav` | 16 kHz モノラル 16 ビット | 録音保存が有効なときに書く。既定で有効（REQ-4.4）。2 チャンネル合わせて 1 時間あたり約 230 MB |
| `meta.json` | 開始・終了時刻、使ったデバイス名、モデル、設定 | 開始時と停止時に書く |

`transcript.jsonl` の 1 行:

```json
{"start": 12.34, "end": 15.80, "speaker": "remote", "text": "では始めましょう。", "wall_start": "2026-10-21T10:00:12.340+09:00"}
```

`start` と `end` は記録の原点からの秒数、`wall_start` は記録開始時の壁時計に `start` を足した値である。

`transcript.md` の 1 行:

```markdown
- `00:00:12` **相手**: では始めましょう。
```

追記の順は確定順なので、2 チャンネルの発話が前後して並ぶことがある。停止時の書き直しで開始時刻順に揃える。

### 3.5 設定

`config.toml` を読み、同名のコマンドライン引数で上書きできるようにする。

| 項目 | 既定値 |
|---|---|
| `port` | 8765 |
| `language` | `ja` |
| `model` | `whisper-large-v3-turbo`（`model_dir` の下のディレクトリ名。2026-10-22 改訂案） |
| `compute_type` | `int8_float16` |
| `cpu_model` | `whisper-small`（同上） |
| `model_dir` | `./models` |
| `headset_keywords` | `["Headset", "ヘッドセット", "Headphone", "ヘッドホン", "Jabra", "Poly", "Logi"]` |
| `save_audio` | `true` |
| `output_dir` | `./output` |
| `silence_warning_sec` | `120`（0 で無効。REQ-2.7, 2.8 の一定時間） |

### 3.6 無音の警告の判定（REQ-2.7, 2.8、2026-10-22 追加）

「音がない」は、そのチャンネルで発話が検出されていないこととする。判定には 3.2 の Silero VAD の発話確率を使い、確率が開始のしきい値（0.5）以上になった窓を「発話あり」とする。音量で判定しないのは、マイクには室内の雑音が常に入り、音量だけでは人が黙っているかを判断できないためである。

時間は、受信した音声の標本位置で数える（壁時計を使わない）。記録の「現在位置」は、両チャンネルの受信済み位置の大きい方とする。片方のチャンネルの音声が届かなくなっても、もう片方が届いていれば時間が進み、届かないチャンネルは無音として扱われる。

| 警告 | 起点 | 出す条件 | 消す条件 |
|---|---|---|---|
| `remote`（REQ-2.7） | 記録の開始位置。`device_changed` を受けたら、その時点の現在位置に置き直す | 起点から現在位置まで、「相手」に発話が一度もなく、その長さが `silence_warning_sec` 以上 | 「相手」で発話を検出したとき。検出した後は、次の `device_changed` まで判定しない |
| `both`（REQ-2.8） | 記録の開始位置と、どちらかのチャンネルで最後に発話を検出した位置の、新しい方 | 起点から現在位置までの長さが `silence_warning_sec` 以上 | どちらかのチャンネルで発話を検出したとき |

- 判定は音声フレームを処理するたびに行い、状態が変わったときだけ `silence` を送る。
- `remote` と `both` は同時に出ることがある。
- 4.3 の引き継ぎで新しい記録になったときは、引き継いだ位置を記録の開始位置として数え直す。
- 判定の結果は `meta.json` に残さない（警告は利用者への通知だけに使う）。

## 4. 通信プロトコル

WebSocket は `/ws` の 1 本で、制御はテキスト（JSON）、音声はバイナリで送る。

### 4.1 音声フレーム（ページ → サーバー、バイナリ）

| 位置 | 型 | 内容 |
|---|---|---|
| 0 | uint8 | チャンネル（0: 自分、1: 相手） |
| 1–3 | — | 予約（0） |
| 4–11 | uint64 LE | 先頭標本の位置（記録の原点からの標本数） |
| 12– | int16 LE × n | 標本（通常 n = 1,600） |

位置を毎フレームに持たせるので、取りこぼしや再送があってもサーバーは正しい時刻に並べられる。サーバーは位置が飛んだ区間を無音で埋め、重複した区間は捨てる。

### 4.2 制御メッセージ（JSON）

| 方向 | `type` | 主な項目 | 用途 |
|---|---|---|---|
| ページ → サーバー | `start` | `language`, `save_audio`, `devices`, `continue`（4.3） | 記録を開始する。サーバーは記録 ID を返す |
| ページ → サーバー | `resume` | `session_id` | 再接続後に記録を続ける |
| ページ → サーバー | `stop` | — | 記録を停止する |
| ページ → サーバー | `device_changed` | — | 記録中にデバイスの変化を検知した（2.2、3.6） |
| サーバー → ページ | `started` | `session_id`, `received`（チャンネルごとの受信済み位置）, `wall_start`, `output_dir` | `start`／`resume` への応答。ページは `received` より後のフレームから送り直す |
| サーバー → ページ | `ack` | `received` | 2 秒ごとの受領確認。ページはこれ以前のフレームをバッファから消す |
| サーバー → ページ | `segment` | `transcript.jsonl` の 1 行と同じ | 確定した発話 |
| サーバー → ページ | `status` | `level`, `message` | GPU が使えないなどの通知 |
| サーバー → ページ | `silence` | `kind`（`remote` / `both`）, `active`, `seconds` | 無音の警告を出す・消す（2.6、3.6） |
| サーバー → ページ | `stopped` | `output_dir`, `segments` | 停止して出力を確定した |
| サーバー → ページ | `error` | `code` | `unknown_session`: `resume` した記録がない（4.3） |

ページとの接続が切れても、サーバーは記録を 10 分間保持して `resume` を待つ。10 分を過ぎたら停止として扱い、出力を確定する。

### 4.3 サーバーの再起動をまたぐ記録の引き継ぎ

記録の状態はサーバーのメモリにしか持たないので、サーバーを再起動すると `resume` は `error`（`unknown_session`）になる。サーバーは停止時に、受信済みの音声の文字起こしを終えてから出力を確定する。ページは `unknown_session` を受けたら記録を止めず、次の項目を付けた `start` を送って新しい記録として続ける。

| 項目 | 内容 |
|---|---|
| `continue.previous_session` | 失われた記録の ID（`meta.json` の `continued_from` に残す） |
| `continue.wall_start` | 元の記録の原点の壁時計。`started` で受け取った `wall_start` を使う |
| `continue.received` | 元の記録でサーバーが受領確認したチャンネルごとの位置 |

サーバーは受信位置と時刻の原点を引き継いだ記録を新しい保存先に作る。ページは送信待ちバッファの残りを送り直す。出力は 2 つのディレクトリに分かれるが、時刻は 1 本の記録として連続する。受領確認は 2 秒ごとなので、前後の記録の境目で最大 2 秒ほど同じ音声が重なることがある（欠けるよりは重なる側に倒している）。

## 5. 実行基盤

### 5.1 WSL2 上で直接実行（REQ-5.1）

`scripts/start.sh` が `uv run mtglog serve` を実行する。サーバーは `127.0.0.1:8765` で待ち受け、起動時に `http://localhost:8765/` を端末に表示する（REQ-6.2）。WSL2 の localhost 転送により、Windows 側の Edge からこの URL で接続できる（V2、確認済み）。

### 5.2 Docker（REQ-5.2）

`docker/compose.yaml` で CUDA 入りのイメージを動かし、`127.0.0.1:8765:8765` だけを公開する。`output/` とモデルのキャッシュはボリュームにする。`scripts/start.ps1` は `docker compose up` を実行して URL を表示するだけで、ほかに Windows 側で処理をしない（C-1）。スクリプトの実行が許されない環境では、同じ `docker compose` コマンドを直接実行する。

コンテナから GPU を使うには、Docker Desktop の WSL2 バックエンドか、WSL の Docker エンジンに NVIDIA Container Toolkit が必要である。どちらもない環境では `docker/compose.cpu.yaml` を重ねて CPU で動かす。

モデルは 5.3 の手順で、ボリュームにした `models/` に準備する（`docker compose run --rm mtglog scripts/setup_models.sh`）。サーバーはモデルを取得しない（REQ-6.1、2026-10-22 改訂案）。

### 5.3 モデルの準備（2026-10-22 改訂）

`scripts/setup_models.sh` が、OpenAI 公式のモデルを取得して faster-whisper 用の形式に変換する（`specs/_steering/tech.md` の「モデルの出どころ」）。GPU の有無にかかわらず、次の 2 つを両方準備する。GPU がある PC でも CPU に切り替わることがあり（REQ-3.5）、その時点で取得できるとは限らないためである。

| 変換後のディレクトリ（`models/` の下） | 取得元（Hugging Face） | 版（コミット） | 保存する型 | ライセンス | 大きさの見込み |
|---|---|---|---|---|---|
| `whisper-large-v3-turbo` | `openai/whisper-large-v3-turbo` | `41f01f3fe87f28c78e2fbf8b568835947dd65ed9` | `int8_float16` | MIT | 約 0.8 GB |
| `whisper-small` | `openai/whisper-small` | `973afd24965f72e36ca33b3055d56a652f456b4d` | `int8` | Apache-2.0 | 約 0.25 GB |

版はスクリプトに固定し、Hugging Face 側の更新で中身が変わらないようにする。版を上げるときは、スクリプトと上の表を同じコミットで変える。

手順:

1. 作業用の一時ディレクトリ（`models/.setup-tmp/`）を作る。`HF_HOME` と `UV_CACHE_DIR` をこの中に向け、取得したファイルとツールのキャッシュがほかに残らないようにする。
2. `huggingface_hub` で、固定した版のうち変換に要るファイルだけを取得する（`config.json`、`model.safetensors`、`tokenizer.json`、`preprocessor_config.json`、`generation_config.json` など）。`pytorch_model.bin` など、同じ重みの別形式は取得しない。
3. `uv run --no-project` の使い捨ての環境に、`ctranslate2`（サーバーと同じ版）、`transformers`、CPU 用の `torch` を入れて、`ct2-transformers-converter` で変換する。`tokenizer.json` と `preprocessor_config.json` は変換先にコピーする（large-v3 系は入力の形式をこのファイルから読むため）。
4. 変換先に `SOURCE.json` を書く。取得元、版、変換ツールの版、保存する型、変換した日時、各ファイルの SHA-256 を記録する。
5. 一時ディレクトリを丸ごと消す。

- 変換先がすでにあり、`SOURCE.json` の取得元と版がスクリプトと一致すれば、そのモデルは飛ばす。2 回目以降の実行はすぐ終わる。
- 一時的に必要な空き容量は約 4 GB（取得したファイル、変換ツール、変換結果）。終了時に残るのは変換後の約 1 GB だけである。WSL の仮想ディスクは自動では縮まない場合があることを README に書く。
- `scripts/start.sh` は、モデルのディレクトリがなければ `setup_models.sh` を先に実行する。利用者が別の手順を覚えなくても、初回の起動でモデルが準備される（REQ-5.1）。
- サーバーは、設定した名前のディレクトリが `model_dir` の下になければ、`setup_models.sh` を実行するよう案内して終了する。以前の版が自動で取得した第三者の変換モデル（`models/models--*`）は使わない。README で削除を案内する。
- 開発用 PC で、変換したモデルと、これまでの第三者の変換モデルで、テスト用の音声の文字起こしが一致するかを比べる（tasks で行う）。

## 6. 検証項目と、確かめ方

| ID | 確かめること | 確かめ方 | 否定されたときの対応 |
|---|---|---|---|
| V1 | 本番 PC の Edge で画面共有とマイクが使えるか | 検証用ページで両 API を呼ぶ | この方式は成り立たない。要件から見直す |
| V2 | Edge から WSL のサーバーに localhost で接続できるか | 確認済み（2026-10-21、利用者が確認） | — |
| V3 | `windowAudio: "window"` で Teams のウィンドウの音だけが取れるか | Teams のウィンドウを共有し、通知音を鳴らして混ざらないことを確かめる | 画面全体の共有のまま（REQ-2.3 は案内しない） |
| V4 | 会議中に Edge の画面共有を続けても Teams の会議に影響がないか | テスト会議で 30 分試す | 影響の内容によって判断する |
| V5 | 背景タブで取得と送信が続くか | タブを背景にして 10 分間記録し、欠落を数える | 取得ページを別ウィンドウで開くよう案内する |
| V6 | 本番 PC で `http://localhost` を開けるか | 確認済み（2026-10-21、利用者が確認） | — |
| V7 | 画面共有の映像トラックを止めても音声トラックが続くか | 検証用ページで映像トラックを止め、音声が続くかを見る | 続くなら 2.3 の 4 を「映像トラックを止める」に変える |

V2 と V6 は確認済みである。残る V1, V3〜V5, V7 は、1 つの検証用ページと最小のサーバーで一度に確かめられる。これを最初の実装タスクにする。

## 7. テスト方針

| 対象 | 方法 |
|---|---|
| 取得ページの純粋関数（浮動小数点→16 ビット変換、フレームの組み立て、初期デバイスの選択、送信待ちバッファ） | `node --test` |
| 無音の警告の判定（3.6） | `pytest`。発話の有無を与える関数を差し替え、起点・出す条件・消す条件・`device_changed` を確かめる |
| サーバーの `segmenter`、`writer`、プロトコル処理 | `pytest`。音声は合成した無音と録音済みの WAV を使う |
| 文字起こしの精度と遅延 | 録音済みの日本語会議音声（数分）を流し込む結合テスト。遅延の中央値を測る（REQ-3.3） |
| ブラウザーと実デバイスを含む全体 | 本番 PC で手動確認。チェックリストを `tasks.md` に置く |
