# 実装タスク: 会議音声のローカル文字起こし

タスクは上から順に 1 つずつ実装する。各タスクの「完了条件」をすべて満たしたらチェックを付ける。「手動」と書いた条件は本番 PC で利用者が確かめ、結果を「検証結果」の節に記録する。

## フェーズ 0: 検証（実装に入る前に方式の成否を確かめる）

- [x] **T0.1 検証用ページと最小サーバー**（design 6章）
  - 内容: `spike/` に、静的ページを配信して WebSocket で受けたバイナリのバイト数と受信時刻だけを記録する最小の FastAPI サーバーと、次の操作ボタンを並べた検証用ページを作る。
    - マイクを開く（`getUserMedia`）
    - 画面全体＋システム音声を共有する（`getDisplayMedia`）
    - ウィンドウ＋ウィンドウ音声を共有する（`windowAudio: "window"`）
    - 映像トラックを止める
    - 各トラックの音量メーターと状態（`readyState`）の表示
    - 音声を 100 ミリ秒ごとにサーバーへ送り、欠落数を表示
  - 完了条件: WSL でサーバーを起動し、ページが配信されることを `curl` で確かめられる。検証用のコードは本体（`web/`, `server/`）に混ぜない。
- [ ] **T0.2 本番 PC での検証**（手動、V1, V3〜V5, V7）
  - 内容: T0.1 のページを本番 PC の Edge で開き、design 6章の表の手順で確かめる。
  - 完了条件: 「検証結果」の節に V1, V3〜V5, V7 の結果を記入する。V1 が否定されたら以降のタスクを止め、要件の見直しに戻る。V3・V7 の結果に応じて design を更新し、再承認を得る。

  - 完了条件: 既定値・ファイル指定・引数による上書きの 3 通りを `pytest` で確かめる。
- [x] **T1.3 音声フレームの解釈と並べ替え**（REQ-2.5 / design 4.1）

## フェーズ 2: 文字起こし

- [x] **T2.1 発話区間の切り出し**（REQ-3.2 / design 3.2）
  - 内容: Silero VAD で発話区間を切り出す。閾値・余白・最大長・最小長を設定値にする。
  - 完了条件: 無音のみ・短い物音・通常の発話・25 秒の連続発話の WAV で、期待する区間数と境界（±100 ミリ秒）になることを `pytest` で確かめる。テスト用 WAV は合成音声または自分で録った音声を使い、`server/tests/data/` に置く。
  - 実施メモ: 境界の判定は音量で発話確率を作る VAD と合成音（正弦波）で行った。Silero VAD は Windows の音声合成で作った日本語音声（`server/tests/data/`）で区間が取れることを確かめた。
- [x] **T2.2 文字起こしワーカー**（REQ-3.1, 3.3, 3.5 / design 3.3）
  - 内容: faster-whisper のモデルを 1 つ読み込み、キューを先着順に処理する。CUDA で読み込めなければ CPU 用の設定に切り替える。待ち時間と処理時間をログに出す。
  - 完了条件: モデルを差し替えたワーカーで順序と切り替えの処理を `pytest` で確かめる。実モデルでは、日本語の WAV を流して文字列が返ることを、GPU がある場合だけ実行する結合テストで確かめる。
- [x] **T2.3 結果の書き出し**（REQ-3.4, 4.1, 4.2, 4.4 / design 3.4）
  - 内容: 記録ごとのディレクトリを作り、`transcript.jsonl` と `transcript.md` へ追記する。停止時に Markdown を開始時刻順に書き直す。録音保存が有効なら WAV を書く。`meta.json` を書く。
  - 完了条件: 追記の直後にファイルを読んで行が増えていること、停止時の並べ直し、WAV の形式（16 kHz・モノラル・16 ビット）を `pytest` で確かめる。
- [x] **T2.4 サーバー全体の結合**
  - 内容: 受信→区間の切り出し→文字起こし→書き出し→`segment` 送信をつなぐ。`mtglog serve` コマンドと `scripts/start.sh` を作る。
  - 完了条件: 録音済みの 2 チャンネルの WAV をテスト用クライアントから実時間で送り、出力ファイルとページへの `segment` に両チャンネルの発話が正しい話者区分で出ることを確かめる。発話終了から `segment` 送信までの遅延の中央値を測り、5 秒以内であること（REQ-3.3、GPU 使用時）。
  - 実施メモ: 遅延は発話終了から約 0.5 秒（GPU、RTX 3050、2026-10-21）。`MTGLOG_GPU_TESTS=1 uv run pytest tests/test_integration_gpu.py` で測れる。

## フェーズ 5: スピーカーの案内と無音の警告（2026-10-22 追加）

- [x] **T5.1 無音の警告の判定**（REQ-2.7, 2.8 / design 3.5, 3.6, 4.2）
  - 内容: `server/src/mtglog/silence.py` に、チャンネルごとの発話の有無と受信位置から `remote` と `both` の警告を判定するクラスを書く。発話の有無は `Segmenter` が評価した窓の発話確率（開始のしきい値以上）から取る。設定に `silence_warning_sec`（既定 120、0 で無効）を加える。`Session` から呼び出し、状態が変わったときに `silence` メッセージを送る。`device_changed` を受けて `remote` の起点を置き直す。4.3 の引き継ぎでは、引き継いだ位置を起点にする。
  - 完了条件: `pytest` で次を確かめる。記録の開始から相手の発話がないまま設定時間がたつと `remote` が出る。相手の発話で `remote` が消え、その後は `device_changed` まで出ない。`device_changed` の後に再び判定する。両方の発話がないまま設定時間がたつと `both` が出て、どちらかの発話で消える。片方のチャンネルだけ音声が届く場合も時間が進む。0 を設定すると出ない。WebSocket 経由で `silence` メッセージが届く。
  - 実施メモ: `silence.py` の `SilenceMonitor` と、`Segmenter.last_voice`（最後に発話を検出した位置）を追加した。再接続（`resume`）のときは、出ている警告を送り直す。`server/tests/test_silence.py` の 10 件を含め、49 件が成功（2026-10-22）。
- [x] **T5.2 スピーカーの表示と警告の表示**（REQ-1.3, 1.6, 2.7, 2.8 / design 2.1, 2.2, 2.6）
  - 内容: 取得ページのデバイス欄に「スピーカー（相手の声の取得元）」の行と案内、サウンド設定を開くリンクを加える。記録中の `devicechange` で `device_changed` を送る。`silence` を受けて、閉じるボタン付きの警告を出す・消す。警告の文を作る関数は `lib.js` に置く。
  - 完了条件: `node --test` で警告の文の組み立て（`remote`、`both`、分数の表示）を確かめる。外部 URL を検出するテスト（T4.2）が通る。ヘッドレス Chromium で、相手の音声が無音のまま記録すると警告が表示されることを確かめる（設定時間を短くして行う）。
  - 実施メモ: 取得ページに「スピーカー（相手の声の取得元）」の行と案内、`ms-settings:sound` のリンクを加えた。警告の文は `lib.js` の `silenceMessage`。`node --test` 14 件、`pytest` 49 件（外部 URL の検出を含む）が成功。`server/tests/e2e_silence.py`（ヘッドレス Chromium、警告まで 3 秒）で、警告の表示、閉じるボタン、閉じた後に再表示されないことを確かめた。`e2e_browser.py` の通し確認も成功（2026-10-22）。README の記録のしかたと「うまく動かないとき」を更新した。
- [ ] **T5.3 本番 PC での確認**（手動）
  - 完了条件（手動）: 本番 PC の取得ページに、既定の再生デバイスの名前と案内が表示される。Teams のスピーカーを Windows の既定と違うデバイスにして記録すると、設定時間の後に `remote` の警告が出る。自分も相手も黙っていると `both` の警告が出て、話すと消える。
